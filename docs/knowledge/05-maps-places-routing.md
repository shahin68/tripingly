# Tripinly — Maps, Places and Routing (client view)

## The stack

| Part | What the client uses |
|---|---|
| Drawing the map | **Google Maps SDK**: Android via the existing integration (maps-compose if already used), iOS via Google Maps SDK for iOS wrapped in `UIKitView` behind a shared interface |
| Places on the map | Tripinly backend `GET /places/tiles` (our places + OpenStreetMap POIs, by map square) |
| Search box | Backend `GET /places/search` |
| Routes and travel times | Backend `GET /days/{id}/route`, `GET /routes` |
| Best route | Backend `POST /days/{id}/optimize` |

**Not used:** Google Places, Geocoding, Directions or Routes APIs. They cost money per call, and Google's terms forbid storing their place data. The Maps SDK itself is free on mobile.

## Legal rules

1. **Hide Google POIs** with a map style JSON (`poi` → `visibility: off`, keep road and area labels). Otherwise users see Google's cafés and try to tap places we can't use.
2. Never read Google POI data (`onPoiClick` etc.) and never send Google place data to the backend.
3. Keep the Google logo and legal text visible (SDK default; don't cover it with UI; use map padding).
4. Show **"© OpenStreetMap contributors"** on every map screen that shows our places or routes (small text over the map, tappable to openstreetmap.org/copyright; since 2026-11-16 behind an ⓘ (Shahin): the credit shows when the map opens and whenever the credits change, as a route comes or goes, looks exactly as before while open and folds into an ⓘ after the system's recommended reading time (5 s base, `calculateRecommendedTimeoutMillis`), and a tap on the ⓘ opens it again for as long, in portrait and landscape, `MapCredits`; the map buttons never move with it; the OSM Foundation's attribution guidelines allow this on mobile, to be re-checked in the stage 13 legal review), and in Settings → About/Legal. For routes, also "© openrouteservice.org". The API responses contain an `attribution` string; show it.

## Shared map abstraction

Keep map UI code platform-specific but its **state shared**:

```kotlin
// commonMain
data class MapState(
    val camera: CameraState,
    val tripMarkers: List<TripPin>,        // markers of the open trip (numbered, with cover thumbnail)
    val places: List<PlacePin>,            // in-view places (Tripinly or OSM)
    val clusters: List<ClusterPin>,
    val routes: List<RouteLine>,           // decoded polylines
    val alongTheWay: List<PlacePin>,
    val selected: Selection?
)

@Composable expect fun TripinlyMap(state: MapState, onEvent: (MapEvent) -> Unit, modifier: Modifier)
// MapEvent: CameraIdle(bounds, zoom), PinClick(id), MapClick(latLng), MapLongClick(latLng), ClusterClick(...)
```

- Android `actual`: Google Maps (maps-compose or MapView, whichever the repo uses).
- iOS `actual`: `UIKitView` hosting `GMSMapView`, a delegate forwarding events, diffing state into `GMSMarker`/`GMSPolyline`. *(Built: the SDK has no Kotlin binding, so Swift (`iosApp/GoogleMapsSdk.swift`) implements the `GoogleMapsSdk`/`GoogleMap` interfaces of `feature:map` and the shared `GoogleSdkMapView` drives it. The key is `MAPS_API_KEY_IOS` in the root `local.properties`; without it, Apple's map (`AppleMapView`) is shown, which takes no taps.)*
- If the repo already has a different abstraction, extend that instead.

## Pins

| Pin | Look | Source |
|---|---|---|
| Trip marker with photo | Larger round pin with the **cover thumbnail** inside plus day-order number | Trip `markers[].coverThumbUrl` |
| Trip marker without photo | Numbered pin in the day color | Trip markers |
| Place with a photo | Round pin (40 dp) with the place's image (`coverThumbUrl`) inside one thin 1 dp ring of its pin color (normal, hot or along the way; Shahin, 2026-11-15: one stroke, coloured, no second white ring); for places with prominence ≥ `photoPinMinProminence` (90) or a `hotCount` ≥ `photoPinMinHotCount` (3), the first `mapMaxPhotoPins` (100) in pin order (all from `GET /app-config`). The icon shows until the image has loaded | Place shapes' `coverImageId`, `coverThumbUrl` (backend#45) |
| Tripinly place (hot spot, not in trip) | Medium "unselected" pin with category icon and hot count (flame) | `in-view` with `isTripinly: true` |
| OSM place | Small dot with category icon, name only at high zoom | `in-view` with `isTripinly: false` |
| Along the way | Like the other place pins, but violet (`AlongTheWayPinColor`) with a white icon, also when the place was already a pin | `alongTheWay` |
| Cluster | Circle with count | `in-view` cluster items |

- Render thumbnails to bitmaps off the main thread (download with the app's image loader, crop circle). Android: `BitmapDescriptor`; iOS: `UIImage` icon (prefer icon images over `iconView` for performance).
- Built (stage 6): `rememberCoverThumbs` loads each cover through Coil's singleton loader, cached by **photo ID + size**, not by the signed URL (it changes about every hour). Android draws the pin with `MarkerComposable` + `TripMarkerIcon(cover)`, iOS paints it with Skia (`drawCoverPin`). A pin is redrawn only when its number, color or cover changes. A number wider than its circle (the 32 dp pin, or the 18 dp badge on a cover pin) stretches the circle into a pill, so every number fits in the middle (`NumberPill`, iOS `drawNumberPill`; Shahin, 2026-11-15).
- **One pin ring (Shahin, 2026-11-15):** every pin on the map (stops, their number badges, places, photos, dots, clusters) has a single 1 dp ring in `MapColors.PinStroke` (white), set in one place (`PIN_STROKE`, `MapColors.PinStroke`), so its colour changes for all pins at once. Photo pins are the one exception to the colour: their single ring takes their pin color (place, hot or along the way), since the photo hides the fill. The "new" dot keeps its 2 dp ring (`NEW_DOT_RING`).
- **Brand stores get a rounded-square logo pin (Shahin, 2026-11-20):** a place whose `brand` has a `logoUrl` (the server's path, made a full URL in `core:data`, `Brand.logoUrl`) is drawn by `drawPlaceLogoPin`: a rounded square (corners 28% of the side) with the same ring colour, size, z-order, fade, dot, dimming and tap as its round pin, the logo on white with a 1.5 dp margin (white in dark mode too: logos are made for white). The logo wins over a photo. Logos (96 px WebP, a few KB) load through Coil keyed `brand-logo:<url>` and are kept for good (the URL changes with the logo); like a photo pin, a brand pin waits for its logo (`PlacePin.isReady`), and one that fails to load, or a brand without a shown logo (the server's `BRAND_LOGOS_ENABLED` / `BRAND_LOGOS_SHOWN`), keeps the round pin. Same on Android and iOS.
- **"This is a brand store" on a new spot (Shahin, 2026-11-20):** while the spot's name is typed (from 2 letters, debounced 300 ms) the long-press card asks `GET /brands?q=` and, when brands match, shows a "Brand store" row of brand chips (logo or a shop icon) between the name and the kinds of place. A tap ties the spot to that brand (sent as `brandId` with Create), a tap on the picked one unties it; a picked brand stays while the name still says it. People can only pick brands from the server's list. With the server's `BRAND_LOGOS_ENABLED` off the server answers no brands, so the row never shows, and ignores a `brandId`.
- **Dots when zoomed out** (owner, 2026-10-19, like Google Maps): below camera zoom `pinDotBelowZoom` (server, `APP_PIN_DOT_BELOW_ZOOM`, default 14) every place pin, photo pins included, turns into a small dot of its pin color (`PlaceDotSize` 8 dp since 2026-11-21, 10 dp before; the pins' thin ring), so route lines and stops stay readable; zooming back in grows them into pins. The tapped place, stops and clusters stay as they are. The change is instant, with no animation (owner, 2026-10-19: a fade was tried, a scale is too costly on Android; revisit later): Android gives each pin a hidden dot marker from the start and only shows one and hides the other (making or dropping 150 markers mid-pinch lagged, and changing a marker's icon makes every pin blink; each pin's markers sit under one key by place ID so a pin reload doesn't remake them all), iOS changes the icon (Swift `setMarkers`). A real shrink would redraw every pin icon on every frame, which costs battery and blinks on Android. Android reads the live zoom from the camera; iOS reports it from Swift (`onZoomChange`).

## Stop card and photos

- Tapping a stop (pin or chip) centers the camera on it, then opens the **stop card** above the pin, with the same scale-in from its bottom center and the same close-on-any-other-touch as the place card. Info windows are off for stops on both platforms.
- **Trip owner (2026-10-23):** on someone else's trip the header shows "by <owner>" after the created date in the owner's colour (deep orange), and the owner's stops use the same colour on their pins and plan chips; other people's stops stay blue. Your own trips show neither.
- The card shows the image its pin shows (the picked cover, else the place's image, both from the server; a Commons image with its credit, from the place's images asked for once per place per map), the stop's name and its photo count; owners and editors get **Add photos** (system picker: Android Photo Picker, iOS PHPicker, several at once, no storage permission). Picking opens the photo sheet so the uploads are visible. Next to it, the **camera** button opens the in-app camera full screen (live picture, shutter; it asks for the camera permission the first time). A photo uploads the moment it's taken, with no review step, and the sheet opens to show it going up. The sheet's header has the same camera button.
- The camera shows the whole picture (fit, not cropped) so the photo shows what the user saw. The shutter sits under the picture in portrait and beside it in landscape; photos come out upright however the phone is held (Android follows the phone's sensor, iOS uses `AVCaptureDeviceRotationCoordinator`). No zoom or tap-to-focus yet (continuous autofocus). The iOS simulator has no camera and says so.
- Tapping the card opens the **photo sheet** (`StopPhotosRoute`, a bottom sheet with its own view model per stop): the stop's **ranked photo grid** (Shahin 2026-10-24): my uploads and the members' processing and failed photos first, then the stop's photos, the place's popular photos and its Commons images by likes, the stop's own tagged "This trip" while others' share the grid; uploads with progress, Retry and Remove, and a full-screen viewer (swipe; owners and editors make any photo of the grid the cover and delete the stop's own, with confirmation). Comments will go into this sheet in stage 7.
- Uploads run from the app scope (`PhotoRepository`): each image is shrunk to `photoMaxEdgePx` and re-encoded as JPEG at `photoJpegQuality` on the phone (this drops EXIF, location included), sent straight to storage through the signed URL with `photoParallelUploads` at a time, then confirmed. Until real time arrives (stage 9) the app asks for the gallery every 3 s, up to 20 times, while photos are processing, then reloads the stop for its cover and count.

## Stop names

Built 2026-10-10 (Shahin asked 2026-10-08, chose "Number + name"):

- A chip shows the stop's number badge and its name; the pin's title is the name. Numbers come from the stop's position in the day, so they follow deletes and reorders.
- A stop added from a place (pin card, search result of ours) is created with `placeId` and named after the place.
- A tap on the map sends only `location`. The server names it (our public place within 25 m, else the Photon address, else the coordinates, backend#28) and the app takes the name from the create answer. Until it answers, the chip shows "Stop N". A name the user already gave (long press, or a rename while it was sending) is never replaced.
- An address picked in search (house, street, Photon place) opens a card with its address and "Add to day N", which sends its name, location and OSM ids. Cities and larger areas only move the map.
- Stops saved before this keep their old "Stop #N" name until renamed.

## Loading places while browsing

Decided 2026-10-10 (Shahin, "Tiles + prefetch"): places load and draw like Google Maps' own, without a request after the map stops or a hitch when pins appear.

1. Places load by **map square**, not by view: square `level/x/y` is `360 / 2^level` degrees a side on a grid fixed on the map (`PlaceSquare`), at `level = zoom − 2` (about four map tiles a side). `GET /places/tiles?tiles=…&zoom=&limit=200` answers up to 16 squares at once, each like in-view for its area. *(Built: `PlaceRepository.placesIn`.)*
2. The repository gathers the squares asked for within 30 ms (the map asks for a screen's tiles together) into one request per 16 and shares a square that is still loading. A caller that stops waiting doesn't cancel the request. Loaded squares are kept until newer ones push them out (at most 200), **stale-while-revalidate** (Shahin, 2026-10-10): a square older than `placesRefreshSeconds` from `GET /app-config` (default 300 s) is answered at once from what's kept and reloaded in the background, in the same batched request as other squares. Only when the reloaded places differ is the square reported (`PlaceRepository.changedSquares`) and its pins updated when it is in view (only the changed markers change). A failed reload keeps the old places and is tried again the next time the square is asked for; a square that never loaded isn't kept.
3. When the camera rests, the squares in view load (kept ones answer at once); once it has rested 300 ms, the ring of squares around the view loads too (only the ones not loaded yet), so a pan finds its places ready (`MapViewModel.onCameraMove`).
4. Zoomed out (< 14): Tripinly places and server clusters, plus OSM places with a Wikidata entry from zoom 10 while hot spots are few. Zoomed in (≥ 14): OSM pins too. The server's picks are fixed on the map, so panning keeps the same pins (backend #25).
   - Decided 2026-10-13 (Shahin, "Markers"): pins are **native map markers** that keep their size on screen while the camera zooms (tiles stretched between whole zoom levels). `MapViewModel` builds the pin list (`placePins`) when the camera rests, from the loaded squares in view: places inside the view that aren't stops, liked places first (most liked first), then by prominence, at most `mapMaxPins` from `GET /app-config` (default 150). A square that changes or a stop added or deleted rebuilds the list. Panning doesn't reshuffle them: a pin already shown that is still in view stays, with its photo or icon, even past the cap, so a pin on screen never vanishes; places new to the view fill the free places, best first, and pins leave only once they're past the edge margin (2026-11-10). A shown pin also stays when the squares of the new rest don't list it (the server picks each square's places per zoom, so a pinch ending just below a whole zoom, a reload or a square that failed to load left small pins out); only after the camera rests a whole zoom step farther out than its closest rest since the last tidy do the pins the farther squares don't list leave (`MapPins.TIDY_ZOOM_OUT`, 2026-11-10). The map diffs markers by place id, so a pin that stays keeps its marker; new pins fade in (250 ms), except places along the way, which show at once with their route. Pins count as in view 10 % of the view beyond each side (`withPinMargin`), so they come before they show and go only once off screen. On Android a pin that leaves is only hidden (the latest 300), so a pin coming back costs no new native marker (2026-11-10). While the camera moves (a held pin pulling it too), the pins follow the view every 250 ms: worked out off the main thread (`computation` dispatcher), and they only come, never go (the rest tidies up), so few markers change; new pins keep their fade-in (Android ours, iOS the SDK's); every pin, along-the-way ones included, goes on the map in the same frame, so switching the route or a new load shows at once (6 new pins per frame on Android was tried on 2026-11-10 and dropped: pins came in one by one). Places along the way never count toward the pin caps: the client shows every one the server sends (at most 40 today, `ALONG_MAX` in the backend's routing service). Each pin look and cluster count is drawn once into a bitmap and reused; a photo pin's look is its image id, loaded through Coil by that id (`rememberPinPhotos`). Decided 2026-10-17 (C/D in `pins-and-saving-decisions.md`): photo pins, capped per screen.
