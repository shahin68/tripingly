Dependency direction: `androidApp`/`iosApp` → `shared` → `feature:*` → `core:*`. Features never depend on each other (the `tripinly.kmp.feature` plugin fails the build if they do). Each module has one Koin module (`commonModule`, `databaseModule`, `storageModule`, `networkModule`, `dataModule`, `locationModule`, `authModule`, `tripsModule`, `mapModule`, `socialModule`); `shared/di/InitKoin.kt` lists them.

Every module has `commonMain`, plus `androidMain`/`iosMain` only where platform code is needed: ShareManager and Koin bindings in `core:common`, DB builders in `core:database`, the HTTP engine and locale in `core:network`, location and its permission in `core:location`, map view and camera in `feature:map`.

## Architecture pattern

- Clean layers inside each feature: `data` / `domain` / `presentation` packages.
- MVVM + MVI: each screen has `XRoute` (gets the ViewModel from Koin, collects `uiState` with `collectAsStateWithLifecycle`, handles events) and a stateless `XScreen(state, onAction)`. ViewModels expose `StateFlow<State>`, take a sealed `Action` via `onAction`, and send one-shot `Event`s through a `Channel`. `State`, `Action` and `Event` are nested inside the ViewModel class.
- ViewModels call repositories directly; use cases only where they hold a rule (`GetCurrentLocationUseCase`).
- The server is the source of truth. Trips are read from Room (`observe…`) and refreshed from the API; trip, day, member and invite writes go to the API first and the response is saved to Room. Marker add, change, delete, clear day and reorder are optimistic (decided 2026-10-07): `DefaultMarkerRepository` writes them to Room at once with an app-chosen marker UUID, sends them one at a time per trip from the app scope (clearing a day is one `DELETE /days/{id}/markers`), retries a dropped connection twice, and undoes a change that fails and reports it on `MarkerRepository.failures`. It doesn't reload the trip afterwards; the place the server matched is taken from its answer (2026-10-08), and so is the name of a stop added without one (a tap on the map, 2026-10-10). `PendingTripWrites` stops a trip reload from overwriting changes still on their way.

## Map integration

- Common `expect fun GoogleMapView(...)` in `feature/map`.
- **Android:** `maps-compose` `GoogleMap`, `MarkerComposable` with the numbered `TripMarkerIcon` (above), place pins and clusters as `Marker`s (bitmaps per look from `drawPlacePin`/`drawClusterPin`, fading in), the tapped place as a bigger `Marker`, the route as a `Polyline` under the pins, my-location layer, long press. Google POIs are hidden by a JSON map style (`MapStyle.kt`, light and night).
- **iOS:** the "GoogleMapView" actual is the **Google Maps SDK** (`GoogleSdkMapView`) when the app started it with a key: Swift (`AppGoogleMapsSdk`, handed to `MainViewController` like `NativeSignIn`) hosts `GMSMapView` behind the `GoogleMapsSdk`/`GoogleMap`/`GoogleMapListener` interfaces (exported with exact ObjC names); place pins, clusters and stops are `GMSMarker`s set together through `GoogleMapsSdk.setMarkers` (stops drawn by `drawTripPin`), the route a `GMSPolyline` through `setRoute`, and it takes taps, long presses and pin taps. Without `MAPS_API_KEY_IOS` it falls back to **Apple MapKit** (`AppleMapView`, no taps).
- Location (`core:location`): `LocationDataSource` with fused location (Android) and `CLLocationManager` (iOS); the location permission is an `expect/actual` `LocationPermissionController` (`status()`, `request()`, `openSettings()`), re-read whenever the map resumes; the view model decides when to ask, explain or send the user to Settings.
- Places: `PlaceRepository` (`core:data`) for search, places by map square (`PlaceSquare`) and place details; `MapViewModel` loads the squares in view when the camera rests (and the ring around them 300 ms later), builds `placePins` (sized by prominence, capped by `mapMaxPins` from app-config; the first `mapMaxPhotoPins` well-known or liked places with an image are photo pins, drawn by `drawPlacePhotoPin`) and `placeClusters` for the map, opens `PlaceCard` on a pin tap (its images in `PlaceImageStrip` in `PlaceImages.kt`; a tapped image opens `PhotoViewerRoute` in `PhotosSheet.kt`, the same gallery and likes as the Photos sheet (a photo the cached gallery doesn't know reloads it once; one that is gone closes with "This photo is no longer available"), shown in `core:designsystem`'s `PhotoViewer` (the app's one full-screen photo pager, like built in, caller actions in a slot)), and runs the header search. `OsmAttribution` sits bottom left over the map.

## Local models vs API contract

Domain models in `core/model/.../trip/` follow the API (UUIDs, `LocalDate` dates, `role`, `visibility`, server-ordered days and markers). DTO ↔ domain mapping is in `core/data/.../trips/TripMapping.kt`; entity ↔ domain mapping in `RoomTripLocalDataSource`. Room keeps dates as `YYYY-MM-DD` strings and `updatedAt` as epoch millis.

## Build and run

- Android: `./gradlew :androidApp:assembleDebug`. Needs `MAPS_API_KEY=...` in `local.properties` (empty key builds, map tiles don't load).
- Local config lives in the untracked root `local.properties` (a Gradle property with the same name is the fallback, e.g. `-P` in CI): `MAPS_API_KEY`, `MAPS_API_KEY_IOS` (read into `AppBuildConfig` in `shared`), `tripinly.useFakeApi`, `tripinly.devAuthSecret` (staging's developer sign-in secret, never committed) `tripinly.googleWebClientId` (the backend's Google Web client ID; not secret) and `firebase.projectId`, `firebase.senderId`, `firebase.appId`, `firebase.apiKey` (from `google-services.json`, which is never committed; without them the Android app has no push), and for iOS `firebase.ios.appId`, `firebase.ios.apiKey` (from `GoogleService-Info.plist`, never committed; read into `AppBuildConfig` with the project and sender). Debug builds (Android debuggable, iOS debug binary) log every HTTP call in full, OkHttp-style, through Ktor's `Logging` plugin; release builds don't log. iOS Google sign-in uses the GoogleSignIn-iOS package (SPM) with the iOS client ID as `GIDClientID` and its reversed form as a URL scheme in `iosApp/iosApp/Info.plist` (client IDs are not secret, so they are committed). The iOS bundle ID is `com.falcon.tripingly`, matching the Android package; Sign in with Apple needs the capability on the app ID.
- Push on Android: `TripinglyApplication` starts Firebase when the four `firebase.*` values are set and binds `FcmPushMessaging`; `TripinglyMessagingService` shows pushes that arrive in the foreground (the system shows the others, in the same `updates` channel) and passes new tokens on. A tap opens `MainActivity` with the push's `deepLink`, handed to `DeepLinks` (`shared`), which `MainNavigation` follows once signed in: `tripinly://trips/{id}` and `tripinly://markers/{id}` open the trip. The notification permission (Android 13+) is asked as Home opens (`HomeRoute`), before anything is tapped.
- Push on iOS: `MainViewController` starts Firebase through the Swift `AppNativePush` (`iosApp/NativePush.swift`, FirebaseMessaging via SPM) when the four values are set and binds `IosPushMessaging` (`shared/iosMain`). The app delegate (`iOSApp.swift`) passes the APNs token to Firebase and makes `AppNativePush` the notification delegate before launch ends, so a tap that launched the app still reaches `DeepLinks`. Foreground pushes show as banners. The permission is asked as Home opens. Needs a paid Apple Developer account, the APNs key in Firebase and the Push Notifications capability.
- Unit tests: `./gradlew allTests` (Android host tests + common) on any OS; `./gradlew iosSimulatorArm64Test` on macOS.
- iOS framework: `./gradlew :shared:linkDebugFrameworkIosSimulatorArm64`; Xcode runs `:shared:embedAndSignAppleFrameworkForXcode`. iOS deployment target 18.2. The iOS Maps key is `MAPS_API_KEY_IOS` in `local.properties`.
- CI (`.github/workflows/ci.yml`): Android assemble + `allTests` on Ubuntu, then iOS framework link, simulator tests and an `xcodebuild` of the app (Swift code) on macOS, for PRs into `develop`/`master` and pushes to `develop`.
- The Claude cloud sandbox cannot download from Google Maven (`dl.google.com` is blocked), so Gradle builds run in CI, not in the sandbox.

## Gaps and risks

1. **No proactive offline detection.** Offline is noticed when a call fails; writes need a connection (no outbox).
2. **iOS map** is the Google Maps SDK since 2026-10-10; it hasn't been run on a device or simulator yet (no Mac).
3. **The Google logo is covered** by the day tabs and itinerary card on Android (legal rule 3 wants it visible; needs map padding that the camera framing accounts for).
4. **Two message types:** `feature:auth` still has its own `UiMessage`; move it to `core:ui`'s `UiText` when auth is next touched.
5. **No marker rename/reorder UI yet** (repository supports both); invite accept and marker copy have no UI yet.
6. **No architecture or lint checks** beyond module boundaries (no Konsist, detekt or ktlint yet).
